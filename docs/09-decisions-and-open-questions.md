# 결정사항과 남은 질문

Last updated: 2026-05-29

## 1. 확정 결정

### D-001. V2는 Part 탭 중심 구조를 버린다

결정:

- Part 1~6은 사용자 화면의 중심이 아니다.
- 내부 상태나 호환 레이어로만 둔다.

이유:

- 대표가 절차를 직접 운전하면 UX가 무거워진다.
- PM이 실제 운영자처럼 업무를 이끌어야 한다.

### D-002. 대표의 기본 인터페이스는 PM 대화다

결정:

- 대표는 대부분의 일을 PM에게 자연어로 요청한다.
- PM이 목표, 태스크, 산출물, 직원, 결정사항을 정리한다.

### D-003. 업무는 그래프로 관리한다

결정:

- 목표, 태스크, 산출물, 직원, 결정사항을 그래프 노드와 엣지로 관리한다.

이유:

- 실제 업무는 선형 단계보다 관계형 구조에 가깝다.

### D-004. 산출물은 독립 객체와 버전으로 관리한다

결정:

- 산출물은 Part나 턴에 종속하지 않는다.
- 각 산출물은 고유 ID와 버전을 가진다.

### D-005. 상태 저장은 SQLite와 파일 시스템을 함께 쓴다

결정:

- 관계와 상태는 SQLite.
- 산출물 본문과 사람이 읽는 문서는 파일.

이유:

- SQLite는 상태 전이와 관계 조회에 강하다.
- 파일은 사람이 직접 읽고 백업하기 좋다.

### D-006. Ollama는 초기 V2 필수 구성에서 제외한다

결정:

- PM, 직원, 서기는 Codex 모델을 기준으로 설계한다.
- 로컬 LLM은 나중에 선택 기능으로 검토한다.

이유:

- 현재 가장 중요한 것은 PM의 추론 성능과 안정적 구조화다.

## 2. 추천 결정

아직 코드 작성 전이지만 추천하는 방향이다.

### R-001. TypeScript 사용

이유:

- 데이터 모델과 액션 스키마가 중요하다.
- JavaScript보다 상태 변경 오류를 줄일 수 있다.

### R-002. V2 포트는 8788

이유:

- 기존 V1 서버의 8787과 충돌하지 않는다.

### R-003. 초기 공개 버전은 PM 주도 실행부터 시작

이유:

- PM이 필요한 팀을 제안하고 대표가 승인하는 구조를 먼저 안정화해야 한다.

## 3. 남은 질문

### Q-001. UI 프레임워크는 무엇을 쓸 것인가?

선택지:

- React
- Svelte
- 기존처럼 순수 JS

추천:

- React 또는 Svelte.
- V2는 상태가 복잡하므로 순수 JS는 장기 유지보수에 불리하다.

### Q-002. PM 액션은 자동 반영할 것인가, 대표 승인 후 반영할 것인가?

추천:

- 안전한 액션은 자동 반영.
- 목표 변경, 직원 생성, 자동 실행, 산출물 삭제, 외부 행동은 승인 필요.

### Q-003. 직원 세션은 항상 영구 세션이어야 하는가?

추천:

- 캠페인별 직원 세션 ID를 유지한다.
- 실패 시 새 세션으로 이어받을 수 있도록 브리프 파일을 항상 만든다.

### Q-004. 산출물 번호는 어떻게 보여줄 것인가?

추천:

- 내부 ID는 `artifact-uuid`.
- 화면 번호는 캠페인별 `001`, `002`.
- 번호는 바뀌지 않게 한다.

### Q-005. Slack 연동은 언제 할 것인가?

추천:

- 초기 공개 버전 이후.
- 먼저 로컬 PM 운영판과 결정함이 안정되어야 한다.

## 4. 설계 리스크

| 리스크 | 대응 |
| --- | --- |
| PM 액션이 잘못 구조화됨 | 서버 검증과 대표 승인 필요 액션 분리 |
| PM이 너무 수동적으로 답변함 | PM 프롬프트에 주도성, 반론, 추천안 의무화 |
| 산출물 관계가 복잡해짐 | 그래프 뷰와 관련 산출물 표시 |
| 자동 실행이 오래 걸림 | 실행 상태판과 현재 작업 표시 |
| 대표 결정이 누락됨 | 결정함을 홈 최상단에 노출 |
| 파일과 DB가 어긋남 | 산출물 manifest와 DB transaction 순서 관리 |
