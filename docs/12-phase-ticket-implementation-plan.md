# 페이즈 티켓 구현 계획서

Last updated: 2026-05-29

이 문서는 `07-implementation-roadmap.md`의 페이즈와 티켓을 실제 구현 작업 단위로 풀어쓴 실행 계획서다.

로드맵이 "무엇을 만들 것인가"를 정리한다면, 이 문서는 "어떤 순서로, 어떤 파일과 화면을 건드리고, 무엇을 확인하면 완료인가"를 정리한다.

## 1. 티켓 운영 원칙

- 티켓 하나는 가능한 한 독립적으로 끝낼 수 있어야 한다.
- DB 스키마 변경이 필요한 티켓은 마이그레이션과 테스트를 함께 포함한다.
- UI 티켓은 `10-wireframes.md`와 `11-layout-and-design-system.md`를 수용 기준으로 삼는다.
- AI 실행 티켓은 먼저 mock runner로 상태 흐름을 검증한 뒤 Codex runner를 붙인다.
- 산출물은 덮어쓰지 않고 새 버전으로 저장한다.
- 대표가 봐야 하는 화면에는 내부 기술 용어를 노출하지 않는다.
- 각 티켓 완료 시 관련 문서 변경이 있으면 `99-version-log.md`에 기록한다.

## 2. 공통 티켓 완료 기준

모든 구현 티켓은 다음 기준을 기본으로 통과해야 한다.

| 기준 | 설명 |
| --- | --- |
| 실행 | 로컬 앱 또는 해당 테스트가 실행된다. |
| 저장 | 변경된 상태가 DB 또는 파일 시스템에 의도대로 남는다. |
| 복구 | 새로고침 후에도 주요 상태가 유지된다. |
| 오류 | 실패 시 사용자가 이해할 수 있는 메시지가 나온다. |
| 문서 | 구현 중 바뀐 구조가 문서와 충돌하지 않는다. |

## 3. Phase 0. 프로젝트 뼈대와 문서

목표:

- 문서 기준에 맞는 실행 가능한 프로젝트를 만든다.
- 이후 페이즈가 올라갈 수 있는 서버, 클라이언트, DB, 데이터 폴더의 뼈대를 만든다.

| 티켓 | 구현 범위 | 주요 대상 | 완료 기준 | 검증 |
| --- | --- | --- | --- | --- |
| V2-0-01 프로젝트 스캐폴드 생성 | Node/TypeScript 기반 앱 생성, 기본 실행 스크립트, README 초안 | `package.json`, `src/`, `README.md` | 로컬에서 앱 첫 화면이 열린다. | 개발 서버 실행, 첫 화면 접속 |
| V2-0-02 TypeScript/Node 환경 구성 | 서버/클라이언트 빌드, lint/format 기본값, shared 타입 경로 | `tsconfig`, `src/server`, `src/client`, `src/shared` | 서버와 클라이언트 빌드가 통과한다. | build/test 스크립트 실행 |
| V2-0-03 SQLite 연결 | DB 연결 모듈, 초기 마이그레이션, health check | `src/server/storage/db.ts`, `migrations/` | `data/local-company.sqlite`가 생성된다. | DB 파일 생성 확인, health API 확인 |
| V2-0-04 기본 폴더 생성기 | `data/` 루트와 사업부/캠페인 폴더 생성 유틸 | `file-store.ts`, `data/` | 기준 폴더 구조가 자동 생성된다. | 폴더 생성 테스트 |
| V2-0-05 문서 색인 정리 | 구현 기준 문서 목록과 읽기 순서 점검 | `docs/` | 구현자가 필요한 문서를 순서대로 찾을 수 있다. | 색인과 폴더 구조 문서 비교 |

Phase 0 완료 시점:

- `http://127.0.0.1:8788`에서 빈 앱 셸을 볼 수 있다.
- DB와 `data/` 폴더가 준비된다.
- 이후 티켓이 사용할 공통 타입과 저장소 계층이 존재한다.

## 4. Phase 1. 캠페인과 PM 대화

목표:

- 대표가 사업부를 보고, 캠페인을 만들고, PM과 대화할 수 있다.
- 이 단계의 PM은 먼저 mock 응답으로 시작해도 된다.

| 티켓 | 구현 범위 | 주요 대상 | 완료 기준 | 검증 |
| --- | --- | --- | --- | --- |

| V2-1-02 캠페인 생성 | 새 캠페인 모달, campaign insert, 캠페인 폴더 생성 | `campaign-service`, 새 캠페인 모달 | 캠페인을 만들고 사업부 홈 목록에 표시한다. | 캠페인 생성 후 DB/폴더 확인 |
| V2-1-03 PM 생성/배정 | 사업부 리드 또는 기본 PM 직원 생성, 캠페인에 PM 연결 | `workers`, `campaigns.pmWorkerId` | 캠페인 생성 시 PM이 자동 배정된다. | 캠페인 상세에서 PM 표시 |

| V2-1-05 PM 답변 실행 | PM runner 인터페이스, mock PM, Codex runner 연결 준비 | `agent-runner`, `prompts/pm.ts` | 대표 메시지에 PM 답변이 생성되어 대화에 추가된다. | mock 응답 테스트, 실패 메시지 확인 |

Phase 1 완료 시점:

- 대표는 사업부 홈에서 캠페인을 만들 수 있다.
- 캠페인 운영판에서 PM 대화 패널을 사용할 수 있다.
- 대화는 DB와 `conversation.md`에 남는다.

목표:

- PM 대화가 목표, 태스크, 산출물 요청, 대표 결정 같은 공식 상태로 반영된다.
- 대표에게는 자연어 답변과 운영판 상태만 보여준다.

| 티켓 | 구현 범위 | 주요 대상 | 완료 기준 | 검증 |
| --- | --- | --- | --- | --- |

| V2-2-02 서기 액션 추출 | PM 답변에서 액션 후보 추출, mock scribe, raw output 저장 | `prompts/scribe.ts`, `events` | PM 답변에서 액션 후보 목록이 나온다. | 샘플 PM 답변 파싱 |
| V2-2-03 액션 검증 | 참조 ID 확인, 위험 액션 분리, 대표 승인 필요 플래그 | `pm-action-service` | 잘못된 참조나 위험 액션이 공식 상태에 반영되지 않는다. | 거부 케이스 테스트 |

Phase 2 완료 시점:

- PM의 답변이 공식 상태 후보로 구조화된다.
- 안전한 액션은 운영판에 반영된다.
- 위험하거나 대표 결정이 필요한 액션은 결정함으로 보낼 준비가 된다.

- 캠페인 운영판에는 요약만, 본문은 산출물 뷰어에서 보여준다.

Phase 3 완료 시점:

- 산출물은 캠페인 상태와 별도로 관리된다.
- 최신 버전과 과거 버전을 구분할 수 있다.
- 대표는 산출물을 문서처럼 읽을 수 있다.

목표:

- PM이 직원에게 일을 맡기고, 큐를 통해 산출물 생성을 실행할 수 있다.
- 초기 구현은 PM 팀 제안 승인과 mock runner 실행까지 검증한다.

| 티켓 | 구현 범위 | 주요 대상 | 완료 기준 | 검증 |

| V2-4-02 캠페인 직원 배정 | 캠페인별 worker assignment, 담당자 표시 | `campaign_workers`, 운영판 | 캠페인에 직원을 배정할 수 있다. | 배정 후 작업/산출물 담당자 표시 |

| V2-4-05 큐 실행 | queued -> running -> done/failed 전이, 산출물 생성 연결 | `queue-service`, runner | 직원 실행 결과가 산출물 버전으로 저장된다. | mock worker 실행 |
| V2-4-06 실행 상태판 | 현재 직원, 산출물, 단계, 오류 표시 | 캠페인 운영판 | 자동 실행 중 현재 상태를 볼 수 있다. | 실행 중/실패/완료 상태 확인 |

Phase 4 완료 시점:

- PM이 만든 작업이 큐에 쌓인다.
- 직원 실행 결과가 산출물로 저장된다.
- 대표는 자동 실행이 어디까지 진행됐는지 볼 수 있다.

## 8. Phase 5. PM 리뷰와 자동 재작업

목표:

- PM이 산출물을 검토하고, 부족하면 제한된 횟수 안에서 재작업을 요청한다.

| 티켓 | 구현 범위 | 주요 대상 | 완료 기준 | 검증 |
| --- | --- | --- | --- | --- |
| V2-5-01 PM 리뷰 실행 | PM review runner, review 파일 저장 | `prompts/pm.ts`, `artifact_versions.reviewPath` | 산출물별 PM 리뷰가 저장된다. | 리뷰 파일 생성 확인 |
| V2-5-02 통과/재작업 판정 | approved/needs_revision 상태 전이 | `artifact-service`, `events` | 리뷰 결과에 따라 산출물 상태가 바뀐다. | 상태 전이 테스트 |
| V2-5-03 재작업 큐 생성 | needs_revision 대상만 revision queue 생성 | `queue-service` | 미통과 산출물만 재작업 큐에 들어간다. | 통과 산출물 제외 확인 |
| V2-5-04 최대 반복 제한 | attempt/maxAttempts, escalated 상태 | `queue_items` | 실패 루프가 무한 반복되지 않는다. | 반복 제한 테스트 |
| V2-5-05 대표 결정 감지 | PM 리뷰에서 결정 필요 항목 생성, 큐 중단 | `decision-service`, `queue-service` | 결정 필요 시 자동 실행이 멈춘다. | 결정 생성과 큐 blocked 확인 |

Phase 5 완료 시점:

- 산출물은 PM 리뷰를 거쳐 완료 또는 수정 필요 상태가 된다.
- 자동 재작업은 안전한 횟수 안에서만 반복된다.
- 대표 결정이 필요한 순간 자동 실행이 멈춘다.

## 13. 공개 버전 우선 구현 컷

처음 구현은 다음 범위를 먼저 닫는 것을 권장한다.

1. Phase 0 전체
2. Phase 1 전체
3. Phase 2 전체
4. Phase 3 전체
5. Phase 4 중 PM 팀 제안 승인과 mock runner 실행까지

이 컷의 성공 기준:

- 대표가 캠페인을 만든다.
- PM과 대화한다.
- PM 답변에서 목표, 태스크, 산출물 요청이 생성된다.
- 산출물이 파일과 DB에 버전으로 저장된다.
- 승인된 직원이 작업 큐를 통해 산출물을 만든다.

이 범위가 안정된 뒤 Codex 실제 실행, PM 리뷰, 결정함, 수정 플로우를 붙인다.
